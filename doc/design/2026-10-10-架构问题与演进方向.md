# 架构问题与演进方向

- 日期：2026-10-10
- 状态：草案

## 目标与约束

首版架构实现了一个本地单人单任务 agent，使用 FastAPI 后端、React 前端、SQLite 持久化与 DeepSeek Responses 接口。实现细节见 [agent 首版设计](2026-10-10-agent首版.md) 与 [0002：agent 首版决策](../decisions/0002-agent首版.md)。

首版为了降低复杂度做了一些简化设计，但在多会话协作、长任务自主性、执行性能和安全性方面存在结构性瓶颈。本方案梳理这些架构缺陷，并制定针对并发调度、事件总线与工作区隔离的演进设计。

## 架构问题清单

### 1. Agent 核心控制循环与自主性

- **上下文溢出直接终止任务**：`Agent.check_context`（[agent.py](../../backend/src/zhenagent/agent.py)）在 token 用量达到 `context_tokens` 阈值时抛出 `RunStopped("limited")`，强制终止任务并要求用户新建会话。缺少滑动窗口、消息截断与上下文摘要压缩机制。
- **审批拒绝直接结束运行轮次**：`Agent.tool`（[agent.py](../../backend/src/zhenagent/agent.py)）在用户拒绝审批时直接抛出 `RunStopped("denied")` 中断任务。未将拒绝原因作为工具结果返回给模型，导致模型无法根据拒绝反馈自我调整策略。
- **系统提示词硬编码**：`instructions` 写死在 `Agent.loop`（[agent.py](../../backend/src/zhenagent/agent.py)）代码内，不支持模板配置；无法动态注入当前 Git 分支、操作系统环境、目录摘要与依赖信息；声明不加载 `AGENTS.md` 和 skill。
- **协议强耦合 Responses API**：`Responses.generate`（[responses.py](../../backend/src/zhenagent/responses.py)）仅支持流式 `/responses` 规范，缺少对主流 Chat Completions、Anthropic Messages 等接口的抽象适配，无法直接接入本地通用模型服务。

### 2. 并发控制与任务调度

- **全局单任务互斥锁**：`Agent.active`（[agent.py](../../backend/src/zhenagent/agent.py)）为进程级互斥锁，全局同时只能执行一个任务。任一会话处于执行中或等待审批状态时，其余所有会话均返回 409 Conflict。
- **审批状态与进程内存强绑定**：`Agent.approvals`（[agent.py](../../backend/src/zhenagent/agent.py)）依赖内存字典中的 `asyncio.Future`。后端进程重启后，未完成的审批和任务统一被标记为 `interrupted`，无法持久化恢复并断点续跑。
- **共享单一工作目录**：所有会话均使用同一个 `workspace` 路径（[tools.py](../../backend/src/zhenagent/tools.py)）。若开启并发，多个任务同时修改同名文件将产生数据覆盖、Git 冲突以及审批 `fingerprint` 频繁失效。

### 3. 安全隔离与工具执行

- **命令执行缺乏沙箱隔离**：`ToolRunner.command`（[tools.py](../../backend/src/zhenagent/tools.py)）直接通过 `/bin/sh -c` 调用本机命令，保留完整宿主机权限。缺少轻量容器或操作系统级安全沙箱隔离机制。
- **纯 Python 递归搜索性能受限**：`ToolRunner.search`（[tools.py](../../backend/src/zhenagent/tools.py)）依赖 `os.walk` 遍历与逐文件全文匹配，设置了 5000 个文件的硬截断，在大中型代码库中容易漏检且消耗大量 CPU，未集成原生 `ripgrep`。
- **精确单匹配文本替换容错率低**：`ToolRunner.edited`（[tools.py](../../backend/src/zhenagent/tools.py)）要求 `old_text` 在目标文件中唯一出现。面对含重复样板代码或空白字符差异的文件时容易报错失败。

### 4. 通信与渲染数据流

- **SSE 依赖数据库轮询**：`run_events`（[api.py](../../backend/src/zhenagent/api.py)）每个客户端连接均在循环中每 250ms 查询一次 SQLite 的 `events` 表，存在不必要的磁盘与数据库读取开销。
- **前端增量事件触发全量拉取**：前端在 SSE 接收到增量事件后防抖 120ms 触发 `load` 全量重新拉取会话详情（[App.tsx](../../frontend/src/App.tsx)），长会话下伴随大量数据重复传输和 React 大树重渲染。

### 5. 存储层与事务一致性

- **状态更新非原子事务**：`Agent.loop`（[agent.py](../../backend/src/zhenagent/agent.py)）在收到模型响应后，向 `items` 插入数据、更新 `runs.call_count`、插入 `tools` 记录与记录 `events` 分布在多次独立 SQL 操作中，异常退出可能留下不一致的状态记录。

## 方案

针对上述核心瓶颈，演进方案重点落实三项改动：

### 1. 基于 Git Worktree 的工作区隔离并发

- **会话级 Worktree 派生**：创建会话时，在 `.local/worktrees/<session_id>` 建立独立 worktree，绑定专用分支 `zhenagent/session-<session_id>`。
- **独立任务锁**：将全局互斥锁下放到会话维度，各会话独立调度，互不阻塞。
- **审查与合并闭环**：任务执行完成后，Web UI 提供与主分支的差异对比视图，支持一键审查合并（`git merge`）或丢弃分支并清理 worktree（`git worktree remove`）。

### 2. 内存事件总线与前端增量状态管理

- **进程内事件总线**：后端引入基于 `asyncio.Queue` 的广播机制。事件持久化写入 SQLite 的同时直接分发给活跃 SSE 连接，断开重连时凭 `Last-Event-ID` 从 SQLite 读取补齐，消除 250ms 忙轮询。
- **前端增量合并**：前端将全量拉取改为增量合并处理，接收 `attempt.delta`、`tool.started`、`tool.completed` 等事件时直接更新内存状态，仅在初始进入会话或重连后执行全量同步。

### 3. Agent 循环容错与上下文滑动

- **上下文智能管理**：引入基于 token 预算的滑动窗口或摘要生成，当历史逼近上限时自动压缩中间工具执行过程，保留系统说明与任务目标。
- **审批拒绝软着陆**：用户拒绝工具执行后，生成表示拒绝的工具输出返回给模型，允许模型尝试其他只读方案或向用户解释。

## 备选方案与取舍

- **容器沙箱 vs Git Worktree**：容器方案虽能同时隔离命令与工作区，但增加了 Docker 守护进程依赖。首阶段优先采用原生 Git Worktree 实现目录与分支隔离，保持单机零外部依赖。
- **共享工作区文件排他锁 vs 独立 Worktree**：共享工作区锁只能避免写冲突，无法让多任务同时修改不同文件；Git Worktree 允许完全并行开发并在主分支合并。

## 验证与验收

- 多会话并发：创建两个会话，同时执行长耗时命令与写操作，验证双方互不阻塞且无文件竞争。
- Worktree 生命周期：验证会话创建自动建立 worktree、任务完成生成审查 Diff、一键合并后主分支正确更新并成功清理工作目录。
- 事件分发：关闭 250ms 轮询后，验证 SSE 实时接收增量文本无延迟，断线重连能根据游标补齐事件。
