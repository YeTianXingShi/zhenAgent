# 开发流程与文档留存

## 开始任务

先阅读 `AGENTS.md` 和任务相关文档，明确目标与验收标准。编写或修改文档前按项目规则加载 shuorenhua。

从最新的 `main` 创建短期任务分支，如 `feat/任务简称`、`fix/问题简称` 或 `docs/文档主题`。首次初始化在 `main` 完成。

## 按任务留存文档

| 工作内容 | 留存位置 |
| --- | --- |
| 新需求或范围变化 | `doc/requirements` |
| 阅读参考源码、查阅技术文档 | `doc/research` |
| 设计功能、接口或模块 | `doc/design` |
| 确定重要方案及其取舍 | `doc/decisions` |
| 计划或运行消融实验 | `doc/experiments` |
| 实现结果、验证和遗留问题 | `doc/development` |

只更新本次任务涉及的分类。复制对应模板，用实际内容替换提示文字；未发生的工作保留为计划。普通记录使用 `YYYY-MM-DD-主题.md`，ADR 编号规则见 [决策说明](../decisions/README.md)。同一天同类任务可在主题中加简短区分。

记录需求、方案和取舍时，写明原因和影响；保留影响项目的聊天结论。相关文档互相链接，并更新分类索引，重要记录加入 [总索引](../README.md)。

修改已有文档时直接更新当前文件，历史由 Git 保存。改变已接受的决策时新增 ADR，保留旧决策并标明替代关系。

## 公开与本地材料

`doc` 下的正式文档随仓库公开。凭证、私人信息及含这些信息的原始材料存入 `.local`，公开文档只保留可公开的结论和必要背景。

shuorenhua 的上游安装材料和评测记录保存在其原目录中；本项目产生的记录写入 `doc`。

## 完成任务

1. 按验收标准运行适合本次改动的检查，记录实际命令、结果和未执行原因。
2. 更新受影响的文档及开发记录，说明遗留问题。
3. 用 `git status` 和 `git diff --cached` 检查准备提交的内容，运行 `git diff --cached --check`。
4. 按 [提交规范](commits.md) 创建围绕一个完整改动的提交。任务完成后核对工作区状态。
5. 将任务分支合并到 `main` 后同步远程；以 `git status -sb` 核对分支和上游状态。

格式检查、测试框架和 CI 在首个功能设计时确定，当前只执行适合文档与配置的检查。
